# 카페24 골라담기 옵션 UI 과제

## 파일 구성

```
detail.html                                  PC 스킨 수정본 (product/detail.html)
detail.mobile.html                           모바일 스킨 수정본 (아래 "PC/모바일 스킨 분리" 참고)
css/module/product/option-picker.css         골라담기 UI 스타일 (PC/모바일 공용)
js/module/product/option-picker.config.js    표시용 설정값 (뱃지/설명/추천문구/문구 포맷, PC/모바일 공용)
js/module/product/option-picker.js           동기화 로직 (PC/모바일 공용)
test/option-picker.test.js                   순수 로직 유닛 테스트 (Node 내장 test runner)
detail.cafe24-inline.html                    detail.html + css/js를 한 파일로 합친 PC용 배포 버전(아래 참고)
detail.mobile.cafe24-inline.html             detail.mobile.html + css/js를 합친 모바일용 배포 버전
scripts/build-inline.js                      위 두 파일을 생성하는 스크립트 (npm run build:inline)
scripts/cafe24-deploy.js                     배포 자동화 (npm run cafe24:deploy[:mobile])
scripts/cafe24-verify-all.js                 PC/모바일 스토어프론트 병렬 회귀 검증 (npm run cafe24:verify)
.github/workflows/cafe24-deploy.yml          CI(테스트) + 승인 후 CD(배포) GitHub Actions
preview/mock-cafe24.html                     카페24 서버 접속 없이 보는 로컬 미리보기 (npm run preview)
```

**⚠️ PC/모바일 스킨 분리**: 이 테스트몰은 반응형 단일 스킨이 아니라 **PC와 모바일
스킨이 완전히 분리되어 있다(디자인 보관함에 PC/모바일 탭이 따로 있고, 실제
모바일 UA로 접속하면 서버가 `/m/product/detail.html...`이라는 별도 경로로
리다이렉트하는 것까지 확인함). 그래서 `detail.html`(PC)과 `detail.mobile.html`
(모바일) 두 파일 모두 각각 배포해야 실제 모바일 방문자에게도 옵션 UI가
보인다 — 하나만 반영하면 다른 한쪽은 순정 옵션 화면 그대로 남는다.

**방법 A (파일 분리, 권장)**: 카페24 관리자 스마트디자인 편집창에서 `detail.html`을
교체하고, `css`/`js` 두 파일은 스킨 편집창의 파일 업로드(또는 CSS/JS 편집기)에서
위 경로 그대로 올린다. 그래야 `<!--@css(...)-->` / `<!--@js(...)-->` include가
정상적으로 로드된다.

**방법 B (인라인, 파일 업로드 기능을 못 찾을 때)**: 스마트디자인 편집창에 CSS/JS를
별도 경로로 업로드하는 기능이 안 보이거나 안 될 때는, `detail.html` 대신
**`detail.cafe24-inline.html`의 전체 내용을 그대로 복사해서 HTML 소스 편집창에
붙여넣으면 된다.** 이 파일은 `<!--@css-->`/`<!--@js-->` 세 줄을 실제 CSS/JS
내용을 담은 `<style>`/`<script>` 태그로 치환해둔 것뿐, 나머지는 `detail.html`과
100% 동일하다(`npm run build:inline`으로 소스 파일에서 자동 생성 — 소스가
바뀌면 이 명령을 다시 돌려 갱신한다). 어느 방법을 쓰든 결과 화면은 동일하다.
모바일 스킨도 똑같이 `detail.mobile.html` / `detail.mobile.cafe24-inline.html`을
쓰면 된다 — 관리자 편집창의 PC/모바일 탭에서 각각의 "상품상세" 화면에 반영한다.

## 테스트

```
npm test
# 또는: node --test test/option-picker.test.js
```

의존성 설치 없이 Node 내장 test runner만으로 돈다. 대상은 **DOM/카페24 없이도
검증 가능한 순수 로직**뿐이다:

- 옵션 텍스트 → 티어/순번(suffix) 파싱, 옵션가 표시로 가격이 붙는 경우까지 포함
  (실제로 이 케이스에서 티어 그룹핑이 깨지는 버그가 있었고, 그 회귀 테스트를 포함함)
- 카페24 필수옵션 표준 플레이스홀더(`value="*"`)가 텍스트와 무관하게 제외되는지
  (실제 테스트몰 배포로 확인한 회귀 테스트 — 아래 "실제 배포로 확인된 것" 참고)
- 품절(disabled) 옵션이 있어도 "추가 가능 횟수 = suffix 개수" 계산이 유지되는지
- 선택 상품 목록 행 텍스트 매칭이 자릿수가 겹치는 다른 티어(예: `100개입_1` vs
  `10개입_1`)를 오매칭하지 않는지
- 같은 옵션을 연속으로 다시 선택해도 매번 `change` 이벤트가 발생하는지(강제 리셋 트릭)
- `select`가 없거나 예상과 다른 형태여도 예외를 던지지 않고 빈 배열을 반환하는지
  (아래 "실패 시 안전장치" 참고 — 이게 깨지면 커스텀 UI 렌더링 전체가 죽는다)

**여기서 검증하지 못하는 것**: 실제 카페24가 `{$form.option}`을 `<select>`로
렌더링하는지, 커스텀 카드가 실제로 뱃지·가격과 함께 그려지는지는 아래 "배포
자동화"로 실제 테스트몰에 배포해 확인했다. 다만 카드의 담기(+)/빼기(−) 버튼을
**클릭했을 때** 카페24 자체 담기/삭제 스크립트가 실제로 반응해 선택 상품 목록에
반영되는지, 반응형 레이아웃이 실제 화면에서 깨지지 않는지는 아직 정적 렌더링
확인까지만 했고 클릭 상호작용까지는 라이브로 확인하지 못했다 — 4번 QA 표와
시크릿창 수동 확인으로 마저 커버해야 한다.

## 배포 자동화 (테스트몰에 직접 반영)

매번 관리자 편집창에 수동으로 복사/붙여넣기 하는 대신, Playwright로 로그인부터
`product/detail.html`(상품상세 화면) 저장까지 자동화하는 스크립트를
`scripts/cafe24-deploy.js`에 추가했다. 계정 정보는 로컬 `.env`(커밋 안 됨)에만
두고, 실행 전 "이 몰이 테스트몰이 맞는지" 대화형으로 재확인한다(하드 룰: 운영몰
작업 금지). 이 흐름은 실제 테스트몰에 대해 로그인부터 저장까지 직접 실행해
검증했다(아래 "실제 배포로 확인된 것" 참고).

**중요한 제약**: 조사 결과 카페24 Admin API에는 구식 스마트디자인(이 프로젝트가
쓰는 `module="product_option"` 같은 템플릿 태그 기반 스킨) 파일을 읽고 쓰는
공식 엔드포인트가 없다 — API로 제공되는 "Design/Themes" 리소스는 별도의 최신
노코드 테마 상품용이다. 그래서 REST API 호출이 아니라 **관리자 편집창을
브라우저 자동화로 조작하는 방식**을 쓴다.

**스킨 종류 주의**: 테스트몰 하나에 스킨이 여러 개 있을 수 있고, 그중 실제로
`product/detail.html`을 통째로 편집할 수 있는 건 **클래식 스마트디자인** 엔진
스킨뿐이다. 신형 "스마트디자인Easy"(노코드 블록 빌더)는 파일을 통째로 열어
텍스트로 바꿔치기하는 화면 자체가 없어서 이 스크립트가 못 쓴다. `cafe24-deploy.js`는
스킨 이름을 하드코딩하지 않고 "디자인 보관함"에서 `[대표디자인]` 표시가 붙은
스킨을 찾아 그걸 연다 — 편집 중인 스킨이 이미 대표 디자인이므로 저장하면
바로 스토어프론트에 반영되고, 별도의 "대표 디자인 지정" 단계는 필요 없다.

### 최초 1회 설정

```
npm install                      # playwright devDependency 설치
npx playwright install chromium  # 브라우저 바이너리 설치
cp .env.example .env             # 테스트몰 계정 정보 채우기 (절대 커밋 금지)
```

카페24 관리자 화면 DOM은 공개 문서가 없어서, 위 로그인/스킨 목록/에디터/저장
selector들은 실제 테스트몰에 대해 직접 실행하며 하나씩 확인해 `cafe24-deploy.js`에
반영해뒀다. 그럼에도 카페24가 관리자 UI를 바꾸면 다시 깨질 수 있는데, 그럴 때
쓰라고 `npm run cafe24:record`(Playwright Codegen)를 디버깅용으로 남겨뒀다 —
브라우저가 열리면 로그인부터 저장까지 수동으로 한 번 수행해 실제 동작을 코드로
다시 확인할 수 있다.

### 실행

```
npm run cafe24:deploy:dry-run      # 로그인~상품상세 화면 열기까지만 확인, 저장은 안 함
npm run cafe24:deploy:headed       # 브라우저를 보면서 실제 반영 (처음엔 이걸로 확인 권장) — PC 스킨
npm run cafe24:deploy              # 헤드리스로 실제 반영 — PC 스킨
npm run cafe24:deploy:mobile:headed  # 브라우저를 보면서 실제 반영 — 모바일 스킨
npm run cafe24:deploy:mobile       # 헤드리스로 실제 반영 — 모바일 스킨
npm run cafe24:qa:mobile           # 모바일 뷰 스크린샷 + 옵션 UI/구매버튼 겹침 자동 검사
npm run cafe24:verify              # PC/모바일 스토어프론트를 병렬로 한 번에 회귀 검증(로그인 불필요, 빠름)
```

`cafe24:verify`는 옵션 관련 코드를 고친 뒤 배포 없이도(또는 배포 직후) 빠르게
"아직 다 정상인지"만 확인하고 싶을 때 쓰는 스크립트다. 로그인이 필요 없는
스토어프론트만 보므로 PC/모바일 컨텍스트를 동시에 띄워 병렬로 확인하고, 카드
렌더링·네이티브 위젯·담기/빼기 상호작용까지 한 실행에서 전부 검사한다.

모든 명령이 실행 전에 `npm run build:inline`을 먼저 돌려 `detail.cafe24-inline.html`
(PC)과 `detail.mobile.cafe24-inline.html`(모바일)을 둘 다 최신화한 뒤, 각각의
내용을 대응하는 스킨의 편집창에 반영한다. **PC/모바일은 완전히 분리된 스킨이라
`:mobile` 없는 명령은 PC 스킨에만 반영된다** — 둘 다 반영하려면 두 명령을 각각
돌려야 한다. 실패하면 `scripts/.cafe24-deploy-error.png`에 스크린샷이
남는다(`.gitignore` 처리됨). `CAFE24_ADMIN_PW` 값은 로그인 폼 입력에만 쓰이고
로그/스크린샷 파일명 등 어디에도 출력되지 않는다.

### 실제 배포로 확인된 것

실제 테스트몰에 위 스크립트로 배포한 뒤 로그아웃 상태(시크릿창과 동일 조건)로
스토어프론트를 직접 확인하는 과정에서, 로컬에서는 못 잡는 실제 버그 두 개를
찾아 고쳤다:

1. **`findOptionTable()`이 항상 실패하던 문제** — 템플릿 소스의 `module="product_option"`
   속성은 카페24가 서버 렌더링 시 제거해버려서, 실제 브라우저에 도착하는 HTML에는
   남지 않는다(대신 `table.xans-product-option` 클래스가 남는다). 이것 때문에
   커스텀 옵션 UI 컨테이너(`#optionPicker`)가 항상 빈 채로 렌더링되고 있었다.
   클래스 기반 폴백 selector를 추가해 고쳤다.
2. **가짜 "empty" 카드가 하나 더 생기던 문제** — 카페24 필수옵션의 표준
   플레이스홀더는 `value="*"`인데, 이 테스트몰에서는 그 텍스트가 흔히 가정하는
   "옵션을 선택해 주세요"가 아니라 "empty"로 렌더링됐다. 텍스트만 보고 걸러내던
   플레이스홀더 필터가 이 값을 놓쳐서 "empty"라는 티어 카드가 하나 더 나왔다.
   `value === "*"` 체크를 추가해 고쳤다(회귀 테스트: `test/option-picker.test.js`).
3. **모바일 스킨에서 엉뚱한 행이 숨겨지던 문제** — 네이티브 옵션 행을 찾을 때
   "옵션 테이블의 첫 `<tr>`"을 기준으로 삼았는데, 모바일 스킨은 옵션 테이블
   앞에 배송(국내/해외) 선택 행이 하나 더 있어서 그 행이 대신 숨겨지고 있었다.
   `select.closest("tr")`로 select를 직접 감싼 행을 찾도록 고쳐서 PC/모바일
   구조 차이와 무관하게 항상 올바른 행을 찾는다.

세 수정 다음 재배포로 PC 스토어프론트에서 카드 5개(10/30/50/100개입 +
플레이스홀더 제외)가 뱃지·설명·가격과 함께 정상 렌더링되고, 네이티브 옵션 행이
렌더링 성공 후에만 숨겨지는 것까지 확인했다.

**PC/모바일 스킨이 분리된 걸 확인한 뒤, 모바일 스킨(`detail.mobile.html`)에도
같은 통합을 적용해 배포했다.** 실제 모바일 UA로 접속(`/m/product/detail.html`)해
카드가 뱃지·설명·가격과 함께 정상 렌더링되는 것, `npm run cafe24:qa:mobile`로
옵션 카드와 구매 버튼(고정 버튼 바 포함)이 스크롤 중에도 겹치지 않는 것, 가로
스크롤이 생기지 않는 것까지 확인했다(스크린샷: `qa/screenshots/mobile-product-detail.png`).

### 카드를 실제로 클릭해보는 QA(`npm run cafe24:qa:interaction`)로 찾은 버그 세 개

정적 렌더링 확인 다음 단계로, 카드의 담기/빼기 버튼을 실제로 클릭해 카페24
"선택 상품 목록"에 반영되는지까지 자동으로 검증하는 스크립트를 만들어 돌려봤다
(영상 녹화 포함: `qa/videos/interaction-qa.webm`). 여기서 처음엔 담기를 아무리
눌러도 목록에 전혀 반영되지 않는 걸 발견했고, 원인을 하나씩 좁혀가며 실제로는
**서로 다른 세 가지 버그**가 겹쳐 있었다는 걸 확인했다:

1. **"텍스트버튼" 스타일은 `<select>`가 아니라 별도 클릭 위젯이 진짜였다** —
   `select.value`를 바꾸고 `change` 이벤트를 보내는 기존 방식은 카페24의 실제
   "담기" 로직을 전혀 건드리지 못했다. 실제로는 select 옆에 카페24가 같이
   렌더링하는 `ul.ec-product-button > li[option_value] > a` 위젯을 클릭해야
   했다. `findOptionButtonLink()`로 이 위젯을 찾아 클릭하고, 위젯이 없는
   스킨(순수 select)에서는 기존 방식으로 폴백하도록 고쳤다.
2. **숨겨진 상태에서는 그 위젯 클릭도 씹혔다** — 네이티브 행을 `display:none`으로
   숨긴 채로 위젯을 클릭하면 카페24가 반응하지 않았다(요소의 실제 치수/노출
   여부를 확인하는 것으로 보인다). 처음엔 담기/빼기 클릭 시 네이티브 행을 잠깐
   다시 보이게 했다가 카페24의 목록 갱신이 확인되면 다시 숨기는 방식으로
   고쳤는데, **실제로 써보니 그 사이 화면이 그려져 깜빡임으로 보이는 문제가
   있었다**(사용자 피드백으로 발견). 그래서 접근 자체를 바꿔서, `.optionPickerNativeRow`를
   `display:none` 대신 치수는 1px×1px로 남기고 화면에서만 잘라내는
   ("sr-only") CSS 기법으로 숨기도록 했다 — 실제 테스트몰에서 이 상태로도
   위젯 클릭에 정상 반응하는 걸 확인했다. 덕분에 클릭할 때마다 보였다 숨었다
   하는 로직 자체가 필요 없어져서 깜빡임이 원천적으로 사라지고 코드도 단순해졌다.
3. **`findSelectedListBody()`가 애초에 엉뚱한 곳을 찾고 있었다** — 실제
   "선택 상품 목록"은 `.detailArea` 밖에 있는 `<tbody class="option_products">`
   였는데, `.detailArea table` 범위로 좁혀서 찾다 보니 항상 못 찾고 있었다.
   이 때문에 역방향 동기화(네이티브 → 커스텀) 자체가 전혀 동작하지 않고
   있었다 — 클래스로 먼저 찾고, caption 텍스트 기반 탐색은 범위 제한 없이
   폴백으로 남겼다.

세 버그를 모두 고친 뒤 실제 클릭 QA에서 8개 항목이 전부 통과했다: 담기 1회/2회
후 목록에 정확히 반영(#2), suffix 최대 횟수(2회) 도달 시 담기 버튼 비활성화와
초과 클릭 무시(#4), 빠른 연속 클릭에도 중복 추가 없음(#3), 카드의 담은 개수
표시가 목록과 항상 일치(#7), 빼기 클릭 후 목록/카드 상태가 함께 줄어드는 것까지
전부 실제 클릭으로 확인했다.

### CI/CD (GitHub Actions)

`.github/workflows/cafe24-deploy.yml`에 두 job이 있다:

- **`test`**: push/PR마다 자동 실행, `npm test`(유닛 테스트)만 돈다. 별도 설정 필요 없음.
- **`deploy`**: `test`를 통과해야 시작되고, `cafe24-test`라는 GitHub Environment를
  거친다. main에 push되면(또는 Actions 탭에서 수동 실행하면) job이 "대기 중" 상태로
  뜨고, **그 environment에 등록된 필수 리뷰어가 승인 버튼을 눌러야만** 실제로
  PC/모바일 스킨 배포 + `cafe24:verify` 회귀 검증까지 진행된다. 매 커밋이 검증
  없이 그대로 라이브 테스트몰에 반영되는 걸 막기 위한 안전장치다(오늘 실제로
  `npm test`는 통과해도 라이브 클릭 QA에서만 드러나는 버그가 여러 개 있었다 — 위
  "카드를 실제로 클릭해보는 QA" 참고).

**GitHub 저장소 Settings에서 최초 1회 해야 하는 것** (이 저장소 파일만으로는 불가능):

1. Settings → Environments → New environment, 이름을 정확히 `cafe24-test`로 생성
2. 그 environment의 "Deployment protection rules" → "Required reviewers"에 승인할
   사람 추가
3. 같은 environment 화면의 "Environment secrets"에 `CAFE24_MALL_ID`,
   `CAFE24_ADMIN_ID`, `CAFE24_ADMIN_PW` 추가 (repository secret이 아니라
   environment secret으로 넣어야 이 environment를 쓰는 job에서만 노출된다)

`scripts/cafe24-deploy.js`에는 `--yes` 플래그가 있어서 CI처럼 터미널 입력을 받을
수 없는 환경에서 대화형 확인을 건너뛴다 — 실제 승인은 이 플래그가 아니라 위
GitHub Environment의 리뷰어 승인이 담당한다. 로컬에서 사람이 직접 실행할 때는
이 플래그 없이 돌려서 대화형 확인을 그대로 받는 걸 권장한다.

## 1. 옵션 UI 구현 방식

- 기존 `module="product_option"` 테이블(옵션 select + 수량)은 삭제하지 않고 그대로 둔다.
  다만 옵션 select를 직접 감싼 `<tr>`(`select.closest("tr")`로 탐색)에
  `optionPickerNativeRow` 클래스를 추가해 CSS로만 감춘다(DOM/이벤트는 유지 —
  하드 룰 준수). `display:none`이 아니라 치수는 1px×1px로 남기고 화면에서만
  잘라내는 "sr-only" 기법을 쓰는데, 카페24의 담기 클릭 핸들러가 요소의 실제
  노출 여부(치수)를 확인해서 `display:none`이면 클릭을 무시하는 걸 실제
  테스트몰에서 확인했기 때문이다(아래 "카드를 실제로 클릭해보는 QA" 참고).
  위치(예: "테이블의 첫 행") 기준이 아니라 select 자체를 기준으로 찾는 이유는
  모바일 스킨에서 실제로 확인했다 — 아래 참고.
- 카페24가 담을 때마다 자동 생성하는 "선택 상품 목록"(`tbody.option_products`)
  자체는 그대로 두지만, **각 줄의 수량 증감 컨트롤(`.quantity`)만 CSS로
  숨긴다**(`css/module/product/option-picker.css`). 이 컨트롤로 수량을 직접
  올리면 카드가 세는 "담은 횟수"(suffix 기준 최대 추가 가능 횟수, #4 요구사항)
  와 실제 구매 수량이 어긋나 하드 룰을 우회하는 통로가 되기 때문이다(예:
  "10개입" 카드는 1/2로 보이는데 그 줄 수량만 5로 올려버릴 수 있음). 삭제(×)
  버튼은 그대로 둬서 카드의 "빼기"와 동일하게 계속 동작한다 — 담기/빼기 개수를
  건드리는 컨트롤만 카드로 일원화했다.
- 그 아래 빈 컨테이너 `<div class="optionPicker" id="optionPicker"></div>`를 추가하고,
  `option-picker.js`가 페이지 로드 시 이 컨테이너 안에 골라담기 카드 UI를 렌더링한다.
- 카드 데이터(개입수 티어, 옵션값, 가격)는 하드코딩하지 않고 **네이티브 select의
  `<option>` 목록을 런타임에 파싱**해서 만든다. 즉 카페24 관리자에서 옵션값을
  추가/삭제/가격변경 하면 코드 수정 없이 카드 UI에 자동 반영된다.
- 옵션값 텍스트를 `{개입수}_{순번}` 형태(`10개입_1` 등)로 파싱해 같은 개입수를
  하나의 카드로 묶고, 그 카드 안에 담기(+)/빼기(−) 스테퍼를 둔다. 즉 "옵션값을
  라디오처럼 하나만 고르는" 게 아니라 "개입수 카드에 여러 번 담는" 실제 데이터
  구조(직접입력 + 여러 개 추가)에 맞춘 인터랙션이다.
- 모바일 바텀시트 모달은 채택하지 않고 PC/모바일 모두 인라인 카드 리스트로
  구현했다(아래 "미구현/제한사항" 참고). 구매 버튼과의 겹침 위험을 원천적으로
  없애기 위한 선택이다.
- 색상/타이포/spacing 값은 피그마 시안에서 추출한 `.claude/design/figma-style-tokens.md`
  값을 그대로 사용했다(라디오 자리는 담은 개수를 보여주는 원형 카운터로 대체).
- Figma MCP로 실제 시안 노드(PC 옵션 카드 `2:2087`, 모바일 바텀시트 `2:1650`)를
  직접 열어 우리 구현과 대조했다. 대부분(결제 버튼, 무료배송 진행바, "추가 구성
  상품" 크로스셀, "맛 선택" 서브패널)은 하드 룰(구매 버튼 외형/옵션 무관 영역
  수정 금지, 우리 데이터 구조와 불일치)에 걸려 의도적으로 제외했지만, 실제로
  가져올 만한 디테일 두 가지를 찾아 반영했다:
  - **"총 담은 개수" 요약 바**: 카드 목록 아래에 전체 담은 개수를 보여주는 바를
    추가했다(시안의 "총 수량" 바 참고). 시안에는 그 아래 "선택완료" 버튼도
    있지만 카페24의 바로구매/장바구니가 이미 그 역할을 하므로 가져오지 않았다.
  - **가격 표기 스타일**: "+15,000원"에서 숫자는 SemiBold, "원"만 Regular로
    분리해 시안과 동일하게 표시한다.
  - (검토했지만 시간/리스크 대비 보류: 카페24가 자동 생성하는 "선택 상품 목록"을
    시안의 회색 카드 스타일로 다시 꾸미는 것 — PC/모바일이 마크업이 달라서
    (이번에 실제로 겪음) 안전하게 하려면 더 검증이 필요해 우선순위를 낮췄다.)

## 2. 외부 설정 JS 구조 (`option-picker.config.js`)

```js
window.OptionPickerConfig = {
  ui: {
    title, subtitle, addButtonLabel, removeButtonLabel,
    limitLabel(max), limitReachedLabel, soldOutLabel,
    unitPriceLabel(unit), emptyListText,
    totalCountLabel(count)  // 선택: "총 담은 개수" 바의 개수 표시 포맷, 기본값 "N개"
  },
  tiers: {
    "10개입": { badge, badgeStrong, description },
    "30개입": { ... },
    ...
  },
  defaultTier: { badge: null, badgeStrong: false, description: "" }
}
```

- `tiers`의 key는 옵션값에서 suffix(`_1`, `_2` ...)를 뗀 문자열과 **정확히 일치**해야
  카드에 반영된다. 일치하는 key가 없으면 `defaultTier` 값으로 대체되어 동작은
  깨지지 않는다(다른 작업자가 신규 개입수를 추가해도 에러 없이 기본 카드로 노출).
- 이 파일에는 **실제 추가 가능 횟수나 가격 숫자를 넣지 않는다.**
  - 추가 가능 횟수는 하드 룰(옵션값 suffix 개수 = 최대 추가 횟수)에 따라
    `option-picker.js`가 select의 `<option>` 개수를 세어 계산한다. config에서
    이 숫자를 바꿀 방법을 의도적으로 열어두지 않았다 — 관리자 옵션값 개수와
    화면 표시가 어긋나는 사고를 막기 위함이다.
  - 가격도 select `<option>` 텍스트에 카페24가 자체적으로 노출하는 가격
    표기(`(+12,000원)` 형태, "옵션가 표시" 설정이 켜져 있을 때)를 정규식으로
    추출해서 쓴다. 즉 관리자에서 가격을 바꾸면 카드 가격도 자동으로 맞는다.
    설정 JS는 그 숫자의 **표시 포맷**(예: 개당가격 문구)만 담당한다.

## 3. 카페24 옵션과 동기화한 방식

- **커스텀 → 네이티브**: 카드의 "담기" 클릭 시, 아직 담기지 않은 suffix 변형 중
  가장 앞 순번을 골라 네이티브 옵션을 그 값으로 선택시킨다. 실제 담기/가격
  계산/"선택 상품 목록" 테이블 append는 전부 카페24 자체 스크립트가 처리하며,
  이 코드는 재구현하지 않는다.
  - **처음엔 `<select>`의 값을 바꾸고 `change` 이벤트를 dispatch하는 방식으로
    짰는데, 실제 테스트몰에 배포해 카드를 직접 클릭해보는 QA에서 이게 실제로는
    담기를 전혀 발생시키지 않는 걸 발견했다.** "옵션 스타일: 텍스트버튼"은
    카페24가 `<select>`(항상 `display:none`으로 숨겨져 있음)와 별도로
    `ul.ec-product-button > li[option_value="..."] > a` 위젯을 같이 렌더링하고,
    카페24 자체 "선택 상품 목록에 담기" 로직은 바로 이 `<a>` 클릭에 붙어 있었다
    — select는 그 위젯의 클릭 결과로 따라서 바뀌는 것이었지, select를 직접
    조작한다고 위젯 쪽 로직까지 실행되는 게 아니었다. 그래서 `findOptionButtonLink()`로
    `option_value` 속성이 일치하는 `<li>`의 `<a>`를 찾아 그걸 직접 `click()`하도록
    고쳤다(회귀 테스트: `test/option-picker.test.js`). 이 위젯이 없는 스킨/스타일
    (순수 `<select>` 드롭다운)을 위해 기존 select 조작 방식은 폴백으로 남겨뒀다.
  - (폴백 경로에서만 해당) 같은 개입수를 연속으로 다시 고를 때 `select.value`가
    안 바뀌면 브라우저가 `change`를 발생시키지 않는 문제가 있어, 값을 빈
    문자열로 리셋한 뒤 목표 값으로 세팅해 매번 실제 값 전환이 일어나도록 했다.
  - "빼기"는 직접 행을 지우지 않고, 카페24가 append한 해당 옵션값 행 안의
    삭제 컨트롤(`.option_box_del`)을 찾아 `click()`한다. 삭제/재계산 로직도
    카페24 것을 그대로 사용한다 — **실제 클릭 QA로 검증 완료**(위 "카드를
    실제로 클릭해보는 QA" 참고).
  - 담기/빼기 클릭 직후부터 `MutationObserver`가 실제 변경을 감지하기 전까지는
    "지금 몇 개 담겼는지" 판단 기준이 아직 갱신 전이라, 그 사이 같은 버튼을
    빠르게 다시 누르면 중복 선택될 여지가 있었다. 티어별 pending 잠금을 둬서
    클릭 즉시 버튼을 잠그고, 실제 목록 변경이 확인된 뒤에만 풀리게 했다(카페24가
    선택을 거부하는 경우까지 대비해 4초 타임아웃 안전장치도 포함).
  - 옵션값 텍스트에 "옵션가 표시" 설정으로 가격이 붙는 경우(`10개입_1 (+12,000원)`)
    suffix 파싱이 깨지지 않도록, 가격 꼬리표를 먼저 떼어낸 뒤 티어/순번을
    구분한다.
- **네이티브 → 커스텀**: "선택 상품 목록"(`<tbody class="option_products">`)을
  `MutationObserver`로 감시한다. 행이 추가/삭제될 때마다 각 옵션값 텍스트가
  그 안에 있는지로 담긴 개수를 다시 세어 카드의 담은 개수/버튼 활성화 상태를
  갱신한다. 카페24가 어떤 이유로든(다른 스크립트, 뒤로가기 등) 목록을 바꿔도
  카드 상태가 항상 실제 목록과 일치한다.
  - **처음엔 이 tbody를 `.detailArea table` 범위 안에서 caption 텍스트("상품
    목록")로만 찾았는데, 실제로는 `.detailArea` 바깥에 있어서 항상 못 찾고
    있었다** — 역방향 동기화가 전혀 동작하지 않던 버그였다(실제 클릭 QA로
    발견). `tbody.option_products` 클래스로 먼저 찾고, caption 기반 탐색은
    범위 제한 없이 폴백으로 남겼다.
- 이 왕복 구조 덕분에 카드를 눌러도, 네이티브 옵션에서 직접 골라도, 목록에서
  직접 삭제해도 항상 같은 상태로 수렴한다(#2, #3 요구사항) — 실제 클릭으로
  검증 완료(위 "배포 자동화 > 카드를 실제로 클릭해보는 QA" 참고).

### 실패 시 안전장치 (사이드 이펙트 방어)

이 스크립트가 세운 가정(select 렌더링 방식, 선택 목록 마크업 등)이 실제 카페24
환경과 다를 가능성이 있어, 아래 안전장치를 코드에 넣었다 — 전부 "잘못 추측해도
손님이 구매를 못 하는 사태만은 막는다"는 원칙 하나로 수렴한다.

- **렌더링 실패 시 네이티브로 자동 폴백**: 카드 UI를 그리는 `render()`는 항상
  `safeRender()`를 통해서만 호출된다. 실패하면(`try/catch`) 숨겨뒀던 네이티브
  옵션 행을 다시 보이게 하고 커스텀 UI를 비운다. 특히 **네이티브 행은 첫
  렌더링이 성공한 뒤에만 숨긴다** — 순서를 반대로 하면(먼저 숨기고 나중에
  렌더링) 렌더링이 실패했을 때 옵션을 아예 고를 수 없는 화면이 된다.
- **config 스크립트 로드 순서 무관**: `option-picker.config.js`의 값을 스크립트
  시작 시 한 번만 읽어 캐싱하지 않고, 카드를 그릴 때마다 `window.OptionPickerConfig`를
  다시 조회한다. 두 스크립트를 `detail.html`에 순서대로 넣어뒀지만, 혹시라도
  로드 순서가 바뀌어도(예: 관리자가 include 순서를 바꿈) 문제없이 최신 값을 쓴다.
- **중복 초기화 방지**: 스크립트가 실수로 두 번 포함되는 등의 이유로 `init()`이
  두 번 불려도 두 번째 호출은 조용히 무시한다(중복 `MutationObserver`/중복
  렌더링 방지).
- **오래된 브라우저 방어**: `MutationObserver`가 없는 환경에서는 역방향 동기화만
  건너뛰고(카드 상태가 실시간으로 안 바뀔 수 있음) 초기 렌더링/담기 동작 자체는
  그대로 동작한다.
- **잘못된 DOM 입력 방어**: `parseTiersFromSelect()`는 `select`가 없거나
  `select.options`가 없어도 예외를 던지지 않고 빈 배열을 반환한다(경계값 방어).

**남은 잔여 리스크(라이브 확인 필요)**: 카페24의 "선택 상품 목록에 담기" 클릭
핸들러가 요소의 화면 노출 여부(치수 기반 `:visible` 류 체크)를 확인한다는 걸
실제로 확인했다(`display:none`이면 클릭이 씹혔다 — 위 "카드를 실제로 클릭해보는
QA" 참고). 그래서 네이티브 행을 `display:none`이 아니라 치수는 남기고 화면에서만
잘라내는 "sr-only" 기법으로 숨기도록 바꿨는데, 이 덕분에 같은 원리로 카페24의
"옵션 선택 안 하고 바로구매/장바구니 시도" 검증도 노출 여부를 본다면 오히려 더
안전해진 셈이다(우리 행은 항상 노출된 것으로 체크되니까). 그래도 `<select>`의
`value`가 실제 검증 기준이 아니라 다른 방식(예: 다른 DOM 요소 존재 여부)에
의존할 가능성은 남아 있어서, 옵션을 하나도 안 담은 채 바로구매/장바구니를 눌렀을
때 카페24가 정상적으로 "옵션을 선택해주세요"로 막는지는 아직 직접 클릭해보지
않았다 — 확인이 필요하다.

## 4. 체크리스트 QA — 진행 상황과 확인 필요 사항

`scripts/cafe24-deploy.js`로 실제 테스트몰에 배포하고 로그아웃 상태(시크릿창과
동일 조건)에서 스토어프론트를 직접 확인했다. **정적 렌더링(카드가 뱃지·설명·
가격과 함께 실제로 그려지는지, 네이티브 select가 실제로 찾아지는지)은 이 확인으로
검증됐다.** 다만 카드 버튼을 실제로 **클릭**했을 때의 상호작용(담기/빼기 → 선택
상품 목록 반영, 반복 클릭, 장바구니/바로구매)까지는 이 자동화 확인 범위 밖이라
브라우저로 직접 클릭해보는 수동 QA가 별도로 필요하다.

| # | 요구사항 | 상태 |
|---|---|---|
| 1 | 골라담기 커스텀 옵션 UI 노출 | **실제 테스트몰 배포로 확인함** — 카드 5개(10/30/50/100개입 + 필수옵션 플레이스홀더 제외)가 뱃지·설명·가격과 함께 정상 렌더링됨. select의 `<option>`을 못 찾으면 커스텀 UI를 그리지 않고 기본 옵션을 그대로 노출하도록 방어 처리(구매 흐름 차단 방지) |
| 2 | 네이티브 옵션과 선택 상태/구매 흐름 동기화 | **실제 클릭 QA로 확인함.** 카드 담기 → 네이티브 위젯(`ul.ec-product-button`) 클릭 → "선택 상품 목록" 반영까지 실제로 이어지는 것을 `npm run cafe24:qa:interaction`으로 검증(영상: `qa/videos/interaction-qa.webm`). 이 과정에서 진짜 버그 3개(select 대신 위젯을 클릭해야 함, 숨김 상태에선 클릭이 씹힘, 선택 목록 탐색 범위가 틀림)를 찾아 고쳤다 — 아래 "카페24 옵션과 동기화한 방식" 참고 |
| 3 | 반복 클릭/재선택 시 중복/오류 없음 | **실제 클릭 QA로 확인함.** 같은 티어 2회 연속 담기, 빠른 연속 클릭(3연타)에도 suffix 최대 횟수(2회)를 넘지 않는 것까지 실제 클릭으로 검증 |
| 4 | suffix 기준 추가 가능 횟수 제한 | select `<option>` 개수 기반 자동 계산, config로 숫자 변경 불가하게 설계. 카페24 필수옵션 플레이스홀더(`value="*"`)가 이 계산에 섞여 들어가는 버그와, 최대 횟수 도달 후 담기 버튼이 실제로 비활성화되는 것까지 실제 클릭 QA로 확인. "선택 상품 목록"의 네이티브 수량 증감 컨트롤로 이 제한을 우회할 수 있던 것도 CSS로 숨겨서 막음(실제 클릭으로 삭제는 계속 되고 수량 조정만 안 되는 것 확인) |
| 5 | 개입 수별 금액 계산 · 품목 모두 생성 | 가격 계산 자체는 카페24 엔진 그대로 사용(재구현 안 함). 카드 가격 표시는 실제 배포에서 "옵션가 표시" 텍스트(`+5,000원` 등)가 정상 파싱되는 것까지 확인함 |

## 5. 미구현 항목 · 제한 사항 · 개선 아이디어

- **렌더링과 클릭 상호작용 모두 실제 테스트몰에서 확인했다.** `findOptionTable()`/
  `findNativeSelect()`로 실제 select를 찾아 카드를 렌더링하는 것, 카드
  담기/빼기 클릭이 실제로 "선택 상품 목록"에 반영되는 것(`findSelectedListBody()`,
  `findOptionButtonLink()`, `clickRowDeleteControl()` 전부)까지 `npm run
  cafe24:qa:interaction`으로 실제 클릭해서 검증했다(위 QA 표, "카드를 실제로
  클릭해보는 QA" 참고). 아직 확인 안 한 건 장바구니/바로구매 버튼을 누른
  **이후**의 결제 플로우 자체(우리가 손대지 않은 영역이라 위험은 낮다)와,
  "필수옵션 미선택" 서버측 검증이 select의 `value`가 아니라 화면 노출 여부에
  의존하는지(아래 참고) 정도다.
- 피그마 시안의 모바일 "바텀시트" 모달은 구현하지 않고 인라인 카드로 대체했다
  (모달 오버레이가 구매 버튼 영역과 겹칠 위험을 없애기 위한 의도적 선택).
- 가격 카드 표시는 select 옵션 텍스트에 노출된 가격 문자열 파싱에 의존한다.
  관리자 옵션가 표시 설정이 꺼져 있으면 카드에서 가격 줄만 생략되고 기능(담기/
  빼기/횟수 제한)은 정상 동작한다.
- "맛 선택" 같은 2단계 서브패널은 우리 상품 데이터 구조(개입수 suffix 기반,
  맛 종류 없음)와 맞지 않아 가져오지 않았다(`.claude/design/figma-style-tokens.md`
  참고).
- 개선 아이디어: 실제 몰 확인 후 셀렉터를 고정값으로 좁히면(예: select의 실제
  id/name 확인) 방어 로직을 줄이고 더 단순하게 만들 수 있다.
