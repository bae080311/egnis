# /cafe24-test

`option-picker.js`의 로직이 바뀔 때마다 그에 맞춰 순수 로직 유닛 테스트를 쓰고, README 문서를 동기화하는 스킬이다. 라이브 카페24 접근 없이도 검증 가능한 부분(DOM 파싱/그룹핑/텍스트 매칭/이벤트 트리거)만 대상으로 한다 — 실제 카페24 렌더링·구매 흐름 동작은 `/cafe24-qa`가 다루는 "라이브 확인 필요" 영역이라 여기서 흉내내려 하지 않는다.

## 절차

1. `git diff`(또는 사용자가 지정한 범위)로 `js/module/product/option-picker.js`에서 바뀌거나 새로 추가된 **순수 로직**(정규식, 파싱 함수, 매칭 함수 등 DOM 이벤트·네트워크 없이 입력→출력이 결정되는 부분)을 식별한다. 어떤 로직이 바뀌었는지, 회귀 위험이 있는 케이스(엣지 케이스, 이전에 있었던 버그와 비슷한 패턴)가 뭔지 먼저 정리한다.
2. 새로 추가되거나 바뀐 로직이 아직 `module.exports` 가드(파일 하단, `typeof module !== "undefined"` 블록)로 노출되지 않았다면 추가한다. 브라우저 동작에는 영향이 없어야 한다 — `typeof window`/`typeof document` 가드로 보호되는 코드 경로(초기화, DOM 조회 등)는 건드리지 않는다.
3. `test/option-picker.test.js`에 Node 내장 `node:test`/`node:assert/strict`만 사용해 테스트를 추가/수정한다(새 의존성 설치 금지 — 이 프로젝트는 스킨 커스터마이징용 정적 파일 프로젝트이지 빌드 도구가 있는 프로젝트가 아니다). 커버 대상:
   - 정상 케이스(happy path)
   - 지금까지 실제로 발견됐던 버그류와 같은 계열의 회귀 케이스(예: suffix 정규식이 가격 꼬리표 때문에 매칭 실패하는 문제, 자릿수가 겹치는 다른 티어 간 오매칭)
   - 빈 값/플레이스홀더, disabled(품절) 옵션 등 방어 로직이 있는 경계 케이스
4. `npm test`(= `node --test test/option-picker.test.js`)를 실행해 전부 통과하는지 확인한다. 실패하면 원인이 테스트 실수인지 실제 로직 버그인지 구분해서 고친다.
5. `README.md`를 갱신한다:
   - "테스트" 절: 새로 추가된 테스트가 검증하는 내용을 한두 줄로 요약
   - 관련 있으면 "옵션 UI 구현 방식"/"카페24 옵션과 동기화한 방식" 절도 실제 코드와 어긋나지 않게 맞춘다
   - "테스트로 검증하지 못하는 것"(라이브 카페24 동작) 문구는 그대로 유지 — 유닛 테스트가 늘어나도 이 경계는 항상 존재한다는 걸 분명히 한다
6. 마지막에 무엇을 테스트했고 무엇은 여전히 라이브 확인이 필요한지 요약해서 보고한다. 이 스킬은 `/cafe24-qa`(체크리스트 점검)나 `/cafe24-review`(하드 룰 diff 검토)를 대체하지 않는다 — 이어서 그것들도 돌릴지 사용자에게 물어본다.

## 하지 않는 것
- jest 등 외부 테스트 프레임워크나 새 의존성을 추가하지 않는다(의도적으로 zero-dependency 유지).
- 라이브 카페24 동작(실제 select 렌더링, 담기/삭제 스크립트 반응, 반응형 레이아웃)을 테스트로 흉내내려 하지 않는다 — 이건 테스트 코드가 아니라 실제 몰에서의 수동 QA 영역이다.
- `detail.html`이나 옵션 UI 스코프 밖 파일은 건드리지 않는다.
